# 盲索引长期增长与结构改造评估

日期：2026-10-05。范围：OCR 文本搜索的盲位图索引，包括写入、读取、删除和格式迁移。下文保留实施前的设计评估。

> 后续评估已完成，分片实现与验证见[盲索引分片实施说明](blind-index-sharding.md)。最终采用 **64 KiB 门槛、每片 2²⁰ 个 OCR ID、按需升级**；下文的 16 KiB / 65,536 ID 是早期候选参数，并非最终实现。

## 结论

**值得继续投入一个 1–2 人日的离线原型，优先评估“只对大位图分块”。不建议直接把所有词元都拆成分块，也不建议第一步引入增量日志与后台合并系统。**

依据如下：

1. 当前优化已降低重复页面处理成本，但每次新增 OCR ID 仍会完整读写对应词元的历史位图。高频词元的成本会随历史增长，这个结构性问题仍然存在。
2. 索引大小分布很不均匀：这份快照中，位图大小中位数只有 22 字节，最大的却有 334,376 字节。统一拆分会让大量小位图承担不必要的记录和键开销。
3. 按 65,536 个 OCR ID 一个分片，若只拆分达到 16 KiB 的多容器位图，只涉及 493 个词元；它们已经占全部位图 BLOB 字节的 33.9%。这是比全量重构更集中的优化对象。
4. 推荐方案的主要投入在搜索兼容、删除一致性和迁移恢复。它属于一个中等规模的存储功能，预计 **10–18 人日**，并非修改一个索引器函数即可完成。

若原型不能在当前优化版基础上明显改善大批次耗时，或造成明显搜索回退，应保留现有方案。数据库文件变大本身，不足以证明需要立即迁移索引格式。

## 1. 已知事实与证据边界

当前格式为：

```text
token_hash → 一个包含全部历史 OCR ID 的 RoaringBitmap BLOB
```

一次新增记录会触及多个词元。对每个词元，程序读取整个 BLOB、合并 ID、重新序列化并写回。因此，写入成本主要随“本批触及的所有历史位图的总长度”增长，而非仅随本批 100 条 OCR 的数量增长。

已经完成的优化包括有效行主键查询、有序访问、临时 16 MiB 页缓存预算和 UPSERT。实测与方法见[离线基准说明](lazy-indexer-benchmark.md)。六轮对照中，三组位图更新事务的耗时中位数分别为：

| 本批位图数据量 | 原循环 | 当前优化版 | 降低 |
| --- | ---: | ---: | ---: |
| 4.56 MB | 557 ms | 366 ms | 34% |
| 9.81 MB | 935 ms | 730 ms | 22% |
| 8.61 MB | 821 ms | 652 ms | 21% |

这些是使用实际索引数据重建的加密索引副本、debug 构建和相同 WAL/FULL 设置下的离线结果，包含位图处理与提交，不包含 OCR、文字解密、有效行检查或文本哈希更新。它们不能直接预测真实应用的总延迟。

本报告又对同一份授权快照做了只读格式统计，查询仅涉及 `blind_bitmap_index`。没有查询 OCR 明文、截图、窗口标题或 URL。统计包括解析 Roaring 容器的头部、长度和偏移，并校验每个 BLOB 的解析终点。

| 指标 | 实测值 |
| --- | ---: |
| 原数据库文件大小 | 3,651,801,088 字节 |
| 词元数 | 728,244 |
| 位图 BLOB 总量 | 81,539,632 字节 |
| 位图大小 P50 / P90 / P99 | 22 / 104 / 884 字节 |
| 最大位图 | 334,376 字节 |
| 最大位图容器数 | 52 |
| 最大的 1% 位图占全部 BLOB 字节 | 56.2% |

位图 BLOB 约占数据库文件的 2.2%，但这不是盲索引整表的磁盘占比：尚未计入哈希键、SQLite 索引、页和空闲空间。**这次改造的主要目标应是降低写入放大与长时间持锁，而非显著缩小整个数据库文件。**

下文的分块空间数字是格式推算；没有建成新的分块数据库，也没有实测分块后的搜索或提交延迟。

## 2. 方案比较

| 方案 | 能解决的问题 | 代价与限制 | 粗略投入及判断 |
| --- | --- | --- | --- |
| 保留当前格式，继续调度与批次控制 | 降低部分单次占锁峰值 | 完整历史位图仍需反复处理；小批次可能增加提交和重复写入 | 1–3 人日；适合作为补充 |
| 所有词元按 ID 范围分块 | 新增和删除只更新涉及分片，降低单个写入单元的增长 | 记录数、键开销和搜索装配成本明显上升 | 8–15 人日；本数据分布下性价比一般 |
| **小位图保留单块，大位图晋升为分片** | 针对大位图控制写入量，同时保留大量小位图的低开销 | 需要两种表示、原子晋升和兼容迁移 | **10–18 人日；优先推荐验证** |
| 基础索引加增量表，定期合并 | 前台写入主要追加小增量，可推迟大位图重写 | 查询需合并增量、删除标记；合并任务、积压、恢复和空间管理更复杂 | 20–35 人日；暂不优先 |
| 独立写连接或写队列 | 减少共享 Rust 互斥锁对部分请求的影响 | SQLite 仍是单写者；不会减少历史位图的读写量，需要维护与库切换协调 | 单独约 4–8 人日；不是增长问题的主要解法 |

这些是替代或组合方案的工程估算，不能相加当作总工期。估算假设由熟悉本项目的 Rust 工程师实施并完成评审、回归，允许一次有进度提示的维护过程。高可用在线迁移、旧版本无损降级和新的跨进程写入架构不包含在基础估算内。

## 3. 推荐格式与空间取舍

建议先以 **16 KiB** 为晋升阈值做原型，同时比较 8–32 KiB；分片跨度先使用 Roaring 天然的 **65,536 个 ID**。

```text
小位图：token_hash → 完整位图

大位图：token_hash → 分片目录 / 总大小 / 基数
        (token_hash, shard_id) → 本 ID 范围内的位图

shard_id = ocr_id / 65536
local_id = ocr_id % 65536
```

新记录通常只触及一个或少数分片；过去范围中的分片不需要随本次新增而重写。删除同样可以根据 OCR ID 找到对应分片。分片值继续使用 Roaring 序列化，保留现有词元化和 HMAC 算法。

这里的分片依据是 **OCR ID**，不能把它等同于截图日期。旧截图可能晚于新截图完成 OCR。若要按时间过滤跳过分片，应使用查询实际得到的允许 ID 集合，不能直接由日期猜测 ID 范围。

### 全量分块的成本

对现有每个 Roaring 容器分别编码为一个分片，保持内容不变，得到以下格式估算：

| 指标 | 当前 | 全量分块推算 |
| --- | ---: | ---: |
| 位图记录数 | 728,244 | 2,555,668，约 3.51 倍 |
| 位图 BLOB 总量 | 81.54 MB | 96.16 MB，增加约 17.9% |
| 最大单个 BLOB | 334,376 字节 | 本快照中为 8,208 字节 |

如果每个分片直接重复存储现有哈希键，新增键字节按一份计算约为 **116.96 MB**，再加 BLOB 头部增量，合计约 **131.57 MB**；还没有计入额外索引、记录头和页开销。

因此，单个更新单元变小，并不意味着数据库总量变小。全量分块可能还需要词元字典加整数 `token_id`，进一步扩大迁移和查询改动。是否采用 `WITHOUT ROWID` 也应通过实际页布局测试确定。

### 只分大位图的成本

下面只晋升达到阈值、且包含多个容器的位图。净增记录不含新的分片目录记录，BLOB 和键字节不含 SQLite 页与索引开销。

| 晋升阈值 | 涉及词元 | 覆盖现有 BLOB 字节 | 净增位图记录 | BLOB 头部及一份重复键的新增字节 |
| --- | ---: | ---: | ---: | ---: |
| 8 KiB | 877 | 39.3% | 44,560 | 约 3.21 MB |
| **16 KiB** | **493** | **33.9%** | **25,047** | **约 1.80 MB** |
| 32 KiB | 265 | 27.4% | 13,515 | 约 0.97 MB |

16 KiB 方案只晋升约 0.068% 的词元，避免对几十万个小位图做同等程度的结构扩张。但“覆盖全库 33.9% BLOB 字节”不等于“每批减少 33.9% I/O”：还要测量实际批次是否频繁触及这些词元，以及本批落在哪些分片。

不建议首版自动把分片形式降回单块，以免阈值附近反复转换。删除后可清除空分片；最后一个分片消失时再清除目录。现有全局 ID 的 `u32` 容量检查仍需保留，这次格式调整不应顺便改变整个搜索结果 ID 契约。

| [连接与生命周期](../src-tauri/src/storage/mod.rs) | 接入维护互斥、独立连接排空、`db_generation` 和缓存失效。若另加后台连接，必须让它参与现有备份、关闭及换库协调。 |

建议统一访问层提供“探测词元大小/基数、读取候选集合、加入或移除 ID、遍历并修复索引”四类能力，把格式判断集中起来。不要让删除、搜索、HMAC 迁移分别维护各自的分片 SQL。

普通搜索、时间线和截图界面可以继续使用现有返回结构。WGC、OCR 模型、语义向量/ANN、app-bound 密钥服务、浏览器扩展和 named-pipe 协议没有直接的索引格式改造需求；仍需做相关流程回归。该改造也不会缩短模型推理本身的耗时。

## 5. 收益与风险

**写入收益有明确的结构依据。** 晋升后的常见新增只需读取、合并和写回涉及的分片。以本快照最大的词元为例，更新单个分片的 BLOB 可从处理约 334 KB 降到处理至多约 8.2 KB 的该分片。这只是 BLOB 工作量举例，不能解释为事务加速 40 倍：目录维护、SQL 调用、SQLCipher 页面处理和 FULL 提交仍存在。

**搜索收益需要另行证明。** 不带过滤的搜索仍可能需要读取所有分片；读取同样数量的 ID 时，更多行和序列化头会增加开销。首版宜让访问层组装出与当前一致的位图，尽量保持召回和排名算法；再按实测考虑利用允许 ID 集合跳过分片。读取一个词元的多个分片应使用批量 SQL，避免逐分片独立查询。

**统计必须与位图同时更新。** 搜索当前依赖 BLOB 长度排序和限制工作量，链接评分依赖文档频率。新增、去重、删除和修复应按实际基数差更新目录统计，不能简单按输入 ID 数量加减。

**读写转换存在并发边界。** 词元目录与分片必须在同一事务中发布；读取者要使用一致快照或格式代际重试。否则可能先看到旧单块表示，再在载入时遇到已删除的旧 BLOB，产生暂时漏搜。已有 `data_version` 和结果缓存机制应纳入回归，但不能代替这些一致性约束。

**分块不会消除所有增长成本。** 不带过滤的全历史搜索、全量损坏修复、总分片数和数据库总量仍会增长。稀有词可能在很多历史范围内各出现一次，分块记录开销尤其突出。分块跨度和晋升阈值应由这些分布共同决定。

## 6. 迁移与恢复建议

建议首版采用可续跑、按词元提交的维护迁移，先避免“全程不停写”的双写复杂度：

1. 新版本先具备两种表示的读取能力和统一写入入口，再引入独立格式状态；沿用维护门控和需要认证的命令边界。
2. 只挑选满足晋升条件的旧词元。读取已有哈希和位图，拆成 ID 分片，不需要重新 OCR、重新分词或读取 OCR 明文。
3. 在单个事务内写入分片和目录、移除或替换旧表示并推进迁移游标。失败时整个词元回滚，重启后可重复处理。
4. 迁移期间的新增、删除、HMAC 重建和修复均通过同一个访问层。首版可暂停这些任务，分批提交并显示维护进度。
5. 先验证新旧 ID 集合与统计等价，再完成格式切换。格式迁移与陈旧 ID 清理应分别验收，避免把结果变化混在一起。
6. 覆盖迁移中断、磁盘不足、取消、备份恢复和目录切换。恢复旧快照后应依据快照自己的版本和游标重新判定，不能沿用当前进程的迁移进度。

**新增一个版本标记不会让已发布的旧程序自动拒绝新数据库。** 降级兼容必须明确设计：旧程序可能只读取或更新单块表，造成漏搜或两套表示分叉。可考虑先发布认识格式门禁的兼容版本，或提供将分片重新合并为旧格式的导出/回退工具。

保留旧表也不等于拥有可用的回滚副本；格式切换后的新增、删除会让旧表过时。恢复升级前快照还可能丢掉升级后的新增数据，不能把它作为无损降级方案。基础工期只包含新版本自身的中止、续跑与一致恢复；额外的旧版本兼容方案需单独估算。

## 7. 投入、验收和决策

推荐方案的工作量粗估如下，包含原型，按一名熟悉项目的工程师计算：

| 阶段 | 交付物 | 人日估算 |
| --- | --- | ---: |
| 离线原型 | 比较 8/16/32 KiB 晋升阈值、分片跨度、真实批次 I/O 与空间增量 | 1–2 |
| 统一访问层与搜索接入 | 单块/分片 CRUD、目录统计、原子晋升、搜索装配与评分适配 | 3–5 |
| 删除、修复与 HMAC 路径 | 同一格式契约、重试和状态一致性 | 2–3 |
| 迁移与生命周期 | 版本、游标、进度、备份/恢复和换库处理 | 2–4 |
| 回归与性能验收 | 故障注入、合成增长场景、搜索语义与实际占锁测试 | 2–4 |
| **合计** | **具备发布条件的实现** | **10–18** |

这约对应 2–4 个工作周的完整工程投入，不是承诺工期。连续在线迁移通常还需要约 5–10 人日；更多历史版本兼容和独立写进程应另立范围。AI 可以加快代码和测试编写，但迁移验证、故障分析和性能对照仍需实际完成。

建议在进入生产迁移实现前设立以下验收目标。它们是投资门槛，不是当前已经达到的结果：

- 以当前优化版为基线，实际中大型批次的位图读写字节下降至少 50%，索引事务 P95 降低至少 30%；同时记录 FULL 提交和真实持锁时间。
- 全库搜索 P95 回退不超过 10%，短语、大小写变体、模糊召回、过滤、分页与链接评分通过语义回归。
- 用原始索引和保持分布的合成 5 倍、10 倍历史检查增长曲线；OCR 文本语义测试使用合成内容，无需查询授权快照中的明文行。
- 测量新旧索引的实际 SQLite 页占用、WAL 写入量和迁移峰值空间；空间开销以当前索引实际占用为分母，建议控制在 15% 内，而非与整个截图数据库相比。
- 对提交前后崩溃、删除与晋升交错、取消续跑、损坏 BLOB、旧快照恢复做故障测试；受影响词元的完整 ID 集合必须一致。
