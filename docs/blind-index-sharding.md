# 盲索引分片实施与验证

本次修改保留已有的主键有效行检查、有序访问、临时 16 MiB 页缓存和 UPSERT，并解决大位图更新时反复读写全部历史的问题。离线评估支持实施，生产代码已经接入搜索、删除、修复和 HMAC 重建路径。

## 存储设计

- 达到 **64 KiB**、且横跨多个分片的大位图，在下一次实际更新时转为分片存储。小位图和未更新的历史位图保持原有 BLOB。
- 每片覆盖 **1,048,576 个 OCR ID（2²⁰）**。片内仍使用标准 Roaring 编码，保存全局 ID。常规更新只读写涉及的片。
- 分片边界与 Roaring 的 65,536-ID 容器对齐，目录记录完整位图的精确基数及规范序列化大小，包含 run-container 头部差异。搜索继续按原有大小排序和预算执行；链接评分使用同样的词频。
- 分片表使用普通 rowid 表和 `(token_hash, shard_id)` 主键。没有新增常驻缓存、增量日志或后台合并任务，也没有降低 WAL/FULL 持久性设置。
- 同一个词元只能存在于内联表或分片目录中。词元迁移、片更新、目录统计与 OCR 索引标记由同一个调用方事务提交；错误向上传递并回滚。重复增删不产生写入。

实现集中在 [`blind_index.rs`](../src-tauri/src/storage/blind_index.rs)。应用层通过统一接口探测、读取、添加、删除和替换倒排集合。

| 模块 | 修改与影响 |
| --- | --- |
| `storage/schema.rs` | 检查格式版本，原子创建新布局；启动时不重写历史位图 |
| `storage/migration/bitmap_index.rs` | 惰性索引及 HMAC 重建使用分片写入；保留分段计时；修复按逻辑词元计数并保存进度 |
| `storage/search.rs` | 一次探测两种表示，按完整位图的大小规划，读取时合并所需词元的全部片 |
| `storage/link_scoring.rs` | 分片词元直接读取目录基数，内联词元继续读取位图 |
| `storage/screenshot.rs` | 删除队列在同一事务内解绑索引并删除 OCR 行 |
| 备份、目录迁移、数据库维护 | 沿用整库快照和事务机制；验证了新布局下的加密快照恢复与 VACUUM |

前端、Tauri 命令签名、鉴权和 OCR 模型没有改动。

慢日志中的 `existing_postings` 仍按词元计数，`postings_written` 与搜索 `load` 反映实际处理的 BLOB/片数；字节统计包含片头，但不包含目录记录、SQLite 页和 WAL 开销。

## 升级与兼容性

首次打开旧库时，原表重命名为 `blind_bitmap_inline`，新增 `blind_bitmap_directory` 与 `blind_bitmap_chunks`，并发布 `app_metadata['blind_bitmap_storage_format']='2'`。该步骤通过 SAVEPOINT 原子执行，支持嵌套在初始化事务内；失败或提交前退出不会留下半套布局。**这次修改没有对提供的评估数据库执行升级。**

原名称 `blind_bitmap_index` 变为兼容性保护视图，引用刻意未注册的函数 `carbonpaper_blind_index_v2_required()`。旧版直接访问索引时会报错，避免它只读到内联部分而产生静默漏搜，或继续写入不完整的索引。这不是面向旧版提供的可查询视图。新版启动也会拒绝未知的未来格式版本。

**升级后的数据库不能直接交给旧版应用使用。** 本次没有实现自动降级转换或自动备份。需要回到旧版时，应使用升级前的完整数据备份；恢复旧备份会失去备份之后新增的数据。不能仅通过删除版本标记或重命名表来降级，也不能仅凭旧程序能够启动就认定兼容。

首次触及大位图仍需读取、拆分并写出该词元的历史数据，所以个别批次仍可能出现较长持锁。收益主要来自后续更新只操作相关片；新词元、跨片批次、冷缓存、磁盘提交和 OCR 行哈希更新仍有成本。该设计不承诺任意规模下固定毫秒数。

## 离线评估方法

源库为用户授权的解密快照，大小 **3,651,801,088 字节**。源连接使用只读标志及 `query_only`，唯一数据查询是 `blind_bitmap_index` 的哈希与位图 BLOB；没有查询 OCR 文字、截图、标题或 URL。原文件大小和修改时间保持不变。

测试从 728,244 个词元构建独立的 SQLCipher 索引副本，使用公开的合成测试密钥。5 倍和 10 倍数据通过把同一词元的位图复制到互不重叠的 ID 区间生成，代表**词汇量固定、历史增长**，不是未来真实数据的预测。

- 基线为此前已优化的单 BLOB 格式，使用有序词元、UPSERT 和相同页缓存策略；候选直接调用生产 `blind_index.rs`。
- Windows、AMD Ryzen 7 8845H；release 构建、WAL、`synchronous=FULL`，自动 checkpoint 1,000 页。写事务临时把页缓存从约 2 MiB 提升到 16 MiB，提交后恢复。
- 三组样本来自末尾附近的三个 100-ID 区间，各含 450 / 450 / 359 个词元。每词元增加一个合成 ID，每组十轮；每种格式、每个规模 **30 次写入**，交替先后顺序。
- 表中的写入统计包含首次按需分片，不是预先转换后的稳态成绩。
- 每种格式、每个规模执行 **1,200 次召回样本**：60 组不透明词元组合，20 轮；包含常见大位图。每次使用新的独立 2 MiB 读取连接，计时排除开连接及 SQLCipher 密钥初始化，包含探测、位图读取/解码和交集。
- 召回复现当前的稀有词元优先、4 MiB 单词元阈值及三组后小结果提前停止规则。不是完整搜索 UI、解密、重排或多关键词截图匹配的端到端基准。
- 校验每个修改词元的完整 ID 集合、基数、规范序列化大小，以及两种格式的每个召回结果。原始结果只输出聚合计数与耗时，不输出哈希、ID 或明文。

下列结果来自最终生产代码与独立工具的完整复测，执行期间没有并行运行构建或测试。聚合原始数值保存在[测量结果 JSON](benchmarks/blind-index-sharding.json)。重复运行仍会受到 OS 文件缓存、磁盘及其他后台负载影响。旧的 debug 读取优化报告与此处 release 结果不能直接相减。

| 历史规模 | 基线写入 P50 / P95 | 分片写入 P50 / P95 | 基线召回 P95 | 分片召回 P95 |
| --- | ---: | ---: | ---: | ---: |
| 1× | 158.7 / 188.0 ms | 100.6 / 164.7 ms | 1.220 ms | 1.283 ms |
| 5× 合成 | 819.8 / 1,847.0 ms | 115.8 / 891.8 ms | 4.018 ms | 4.409 ms |
| 10× 合成 | 1,714.1 / 5,474.3 ms | 129.4 / 1,248.9 ms | 7.623 ms | 7.827 ms |

本轮写入中位数降低约 **37%、86%、92%**，P95 降低约 **12%、52%、77%**；平均读取的位图字节减少约 **53%、84%、87%**。召回 P95 增加约 **5%、10%、3%**，绝对差值为 0.06–0.39 ms。索引副本的已用数据库页增加约 **0.14%、0.65%、1.00%**；这不是整个截图数据库的增长率，也不包含瞬时 WAL 占用。

接入阶段另一轮生产接口评估的写入 P95 分别为 **191.9 → 149.4 ms、1,144.2 → 652.0 ms、2,820.9 → 1,234.5 ms**，召回 P95 增幅约 6%、5%、2%。两轮都呈现相同的读写量下降和中位数收益；P95 尤其受磁盘提交影响，不宜把单轮的最大降幅作为性能承诺。

这些数据支持选择性分片，但不等同于 `lazy_indexer_write` 总持锁或用户搜索总耗时同比例下降。写入基准不包含 OCR 解密、分词、有效行检查和 OCR 行哈希更新，也未清空 OS 缓存。早期原型中共享读写缓存或预先全量分片的成绩不作为本结论依据。

## 复现

独立工具位于 [`tools/blind-index-benchmark`](../tools/blind-index-benchmark/src/main.rs)，直接编译生产存储接口，不启动 Tauri。它只接受旧格式、明文的评估副本；不要把它当成生产数据库迁移工具。

从仓库根目录执行：

```powershell
$env:CARBONPAPER_BITMAP_BENCH_DB = 'D:\tools\carbonpaper\data\screenshots_decrypted.db'
$env:CARBONPAPER_BITMAP_BENCH_OUT = "$PWD\src-tauri\target\blind-index-benchmark"
$env:CARBONPAPER_BITMAP_BENCH_SCALES = '1,5,10'
cargo run --release --locked --manifest-path tools/blind-index-benchmark/Cargo.toml
```

结果写入输出目录的 `results.json`，`variant=0` 为基线，`variant=1` 为分片。按 `kind`、`scale`、`variant` 分组，对 `total_ms` 排序，使用 nearest-rank 分位数；30 次写入的 P95 是第 29 个值，1,200 次召回的 P95 是第 1,140 个值。`read_bytes` / `write_bytes` 是位图 BLOB 字节，不是操作系统实际 I/O。`used_bytes` 是扣除空闲页后的数据库页字节。

运行期间需要空间容纳各规模的临时索引数据库和 WAL，首次编译还需构建 vendored OpenSSL。临时数据库由工具自动清理，结果 JSON 保留。为了比较耗时，应避免同时执行构建、测试或应用后台任务。

## 正确性验证

覆盖旧格式读取、按需转换、重复更新、跨片删除、`u32::MAX`、大小写变体、严格/模糊召回及预算、链接评分、删除队列、修复词元计数、旧版访问拒绝、未知版本拒绝和 schema 错误回滚。

使用合成数据库测试了提交前后子进程直接退出的 WAL 恢复，以及加密 `VACUUM INTO` 快照恢复。坏位图导致错误并回滚已经进行的词元转换和索引标记；范围不匹配的片不会被当作正常位图继续使用。

Rust 全量库测试 **805 项通过、3 项按设计忽略**；随后对链接评分批量读取的收尾修改重跑存储测试，**337 项通过、3 项忽略**。忽略项为显式离线基准和由父测试单独启动的崩溃子进程入口。主后端和独立工具的 `cargo check`、安全守卫及变更文件格式检查通过。

全量测试曾有三项回环 HTTP 用例被系统代理截获；设置 `NO_PROXY=localhost,127.0.0.1,::1` 后，针对性测试和全量重跑通过，没有改动该模块。没有启动真实应用，也没有修改授权源库。
