# Agent memory 存储与验证指南

本指南用于验证 `agent-memory.db` 的生成、增量同步和容量改进。它区分前序本地检查已经得到的结果，以及需要在包含 Agent 功能的版本中继续执行的验证。

本分支基于 `main` 的 `6f93375`。该基线尚未包含前序检查使用的 Agent 访问模块；本分支实现的是主库优化，未把另一版本的 Agent 功能移植进来。

## 已有观察

以下数字来自前序本地检查的那个时点，不是本分支迁移后的实测结果。MiB 按 1,048,576 字节计算。

| 项目 | 结果 | 依据和限制 |
| --- | ---: | --- |
| `agent-memory.db` 文件大小 | 619,986,944 字节，591.27 MiB | 文件长度，不含另计的 WAL、SHM 等旁文件 |
| 主库截图数量 | 约 8.5 万张 | 本地聚合统计 |
| 主库 OCR 行数 | 约 377 万条 | 本地聚合统计 |
| OCR 文本本身 | 约 78 MiB | 从 AES-GCM 密文长度扣除每条 28 字节开销估算，不是导出的明文文本文件 |
| 旧 Agent 投影的逐行密钥封装 | 每条 60 字节 | 32 字节行密钥，加 12 字节 nonce 和 16 字节认证标签 |
| 旧投影的逐行摘要 | 每条 32 字节 | 从实现中的记录格式确定 |
| 两项逐行字段的容量估算 | 约 331 MiB | `3,770,000 × (60 + 32)`；尚未计入行头、主键、索引、页内空隙等 |

**没有取得 Agent 副库各表的 `dbstat` 实测分布。** 其访问密钥由服务管理，331 MiB 是格式与行数相乘得到的估算，不能表述成已测得的表占用，也不能据此认定其余空间都是可回收垃圾。

一个准备日志片段记录了 1,646,243 条 OCR 的处理：

| 阶段 | 耗时 |
| --- | ---: |
| 整个片段 | 863.845 秒 |
| 读取 | 103.063 秒 |
| 数据解包和准备 | 472.232 秒 |
| 其中 RSA 解封装 | 258.220 秒 |
| 写入 | 281.644 秒 |

RSA 时间包含在数据准备阶段中，不应再次相加。这是一个日志片段的计时，不是完整数据库构建的端到端基准。

## 副库如何工作

前序检查中的实现复用了主库的 OCR 和向量密文。准备阶段在已有授权上下文中解开 OCR 行密钥，再用独立的 Agent 密钥重新封装，保存对应的来源标识、摘要和投影状态。后续访问依据这些受限材料读取允许的历史内容，并检查来源是否仍然有效。

因此，这个副库保存了大量“读取原始密文所需的材料”。旧主库每条 OCR 都有独立密钥，副库也就为每个很短的文本块存储一套封装和摘要。文件大小随 OCR 块数量增长，不能只用截图张数估计。首次准备还需要处理大量旧 RSA 封装，单纯缩短写事务不能消除这部分时间。

## 与本分支主库格式衔接

Agent 功能合入这一主库版本时，需要先完成以下适配：

| 主库变化 | Agent 读取端需要遵守的契约 |
| --- | --- |
| OCR 的 `text_hash` 成为紧凑的索引状态标记 | 不把它当作文本摘要；检索仍使用盲索引 |
| `ocr_results.ocr_key_id` 引用独立的 OCR 批次密钥 | 同时支持旧逐行 RSA 格式和新组格式；不可把缺少旧封装列误判为空文本 |
| 新 OCR 的认证绑定 | 保留内容数据集、截图 ID、OCR ID、密钥组 ID 和组用途的校验；可参考 `storage/ocr_keys.rs` |
| `derived_embeddings` 的向量可能存于 `vector_blocks` | 使用 `derived_embeddings_read` 取得完整密文，再执行既有来源绑定校验 |
| 应用图标改为共享加密引用 | 图标属于截图展示数据；最小文本投影无需复制它 |

组密钥仅用于 OCR，与图片密钥分开。若 Agent 的授权粒度小于一个 OCR 密钥组，应单独投影被允许的文本，不能把整组密钥等同于逐行授权。副库也不应取得截图内容密钥或主密钥。

主库的在线转换会改变加密表示，同时保留文本内容、行标识和处理版本。Agent 的增量同步应明确区分“内容变化”和“表示变化”：已有密文摘要发生变化时，重新核对来源并更新投影，而不是继续使用不匹配的密钥或将该行静默跳过。

## 容量方案的比较方法

至少使用同一份固定测试历史比较以下方案：

1. **逐行重新封装**：作为兼容性基线，记录当前格式的完整文件组大小。
2. **批量封装旧行密钥**：把若干行密钥放入一个认证加密块。它能摊薄 nonce、标签及记录开销，但随机密钥本身基本不可压缩；377 万个 32 字节密钥仍约需 115 MiB，再加摘要和映射。
3. **最小文本投影**：只打包允许读取的 OCR 文本及必要来源映射，先压缩，再用独立 Agent 密钥加密。文本估算量约 78 MiB，值得与方案 2 实测比较。向量和盲索引尽量复用主库，避免复制图片、图标及完整截图元数据。
4. **复用新的 OCR 组结构**：在授权范围允许时，按组封装并引用主库的 OCR 专用密钥。分别测量密钥材料、逐行摘要和映射的占比，不能只压缩其中一个字段后假定总量会同比下降。

压缩必须在加密前完成。对已有随机密文再做通用压缩通常不会产生有效收益。每个投影块应有独立认证和明确的来源范围，并限制最大解压大小。块大小需要同时考虑空间、单次读取开销、增量更新和删除后的回收成本。

上述方案在这个分支中尚未实现或测得最终大小；不能承诺某个固定的副库容量。

## 验证流程

### 1. 固定样本与计量口径

- 用现有备份或快照流程准备一致的测试副本，记录程序版本、源数据库版本、数据时间范围、截图数、OCR 数、向量数及各阶段耗时。
- 在服务允许的诊断边界内查询 `page_size`、`page_count`、`freelist_count`，以及按表、索引分组的 `dbstat` 聚合。诊断输出只需要数量、长度和时间。
- 同时记录主文件与 WAL 等旁文件的总大小，以及构建期间的磁盘峰值、内存峰值和临时文件总量。
- 分别记录首次准备、增量追加、重启续跑、删除回收四种工作负载。对比整理前后占用时使用相同的 checkpoint 和整理条件。

### 2. 内容与检索一致性

- 覆盖中文、英文、空结果、极短 OCR、大量相同文本、长文本、同一截图中的多个框和重新 OCR 的截图。
- 在同一授权范围内比较文本、框顺序、搜索命中、关联截图和来源版本；语义向量应保持原有精度与模型契约。
- 用完全旧格式、完全新格式和混合格式三种主库测试；后台迁移正在进行时也应得到一致结果。
- 任一范围尚未投影、校验失败或来源已经变化时，返回明确的不可用或未完成状态，避免把缺口当成完整历史中的“没有结果”。

### 3. 授权和生命周期

- 在准备和读取的中途锁定、撤销授权、重新解锁、切换数据集，验证旧请求与旧缓存不会继续发布结果。
- 验证副库只接受独立 Agent 授权，截图和主密钥不进入投影或其密钥清单。
- 在准备与读取过程中删除 OCR、软删除截图、执行物理清理及重新 OCR；验证旧投影和旧来源摘要随之失效。
- 在投影边界、事务提交前后和游标更新处注入故障；重启后应从最后已提交批次继续，保持数据与游标一致。
- 测试块内部分数据删除、整块删除、反复更新与重建，确认空间能够回收，且不会通过清理共享块删除仍被引用的数据。

### 4. 完成条件

容量方案只有在内容等价、授权生命周期、来源校验和故障续跑全部通过后，才进入默认启用的候选范围。记录实测收益及其条件，并把尚未执行的验证单独列出。

目前已完成的是前序文件、主库聚合、格式和日志检查，以及本分支主库的合成测试。Agent 副库的表级实测、候选压缩格式基准、Agent 端新主库格式适配与端到端生命周期验证仍待在包含该功能的版本上执行。
